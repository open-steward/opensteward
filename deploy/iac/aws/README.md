# OpenSteward — AWS / EKS reference Terraform

Reference (example) infrastructure-as-code that provisions exactly what the
OpenSteward AWS Helm overlay expects:
[`deploy/helm/overlays/aws-values.yaml`](../../helm/overlays/aws-values.yaml).

This is an **example an operator adapts**, not a turnkey product. It favours
clarity and correctness over completeness: providers are pinned, the non-obvious
is commented, and no real secrets are hardcoded. Read the overlay first — every
`<PLACEHOLDER>` in it is produced by an output here.

## What it creates

| Resource | Module / type | Notes |
|---|---|---|
| VPC (public + private + database subnets, single NAT) | `terraform-aws-modules/vpc` `~> 5.13` | subnets tagged for the AWS LB Controller |
| EKS cluster + 1 managed node group | `terraform-aws-modules/eks` `~> 20.24` | lean `m6i.large` x2, current K8s; IRSA enabled; EBS CSI add-on for the `gp3` StorageClass |
| RDS for PostgreSQL | `terraform-aws-modules/rds` `~> 6.9` | gp3, encrypted, private; Multi-AZ via `db_multi_az` |
| Secrets Manager `opensteward/app-secrets` | `aws_secretsmanager_secret` | JSON `{JWT_SECRET, SESSION_SECRET, STORE_SECRET}`, generated by the `random` provider |
| Secrets Manager `<prefix>/db-credentials` | `aws_secretsmanager_secret` | DB creds + ready `DATABASE_URL` |
| IAM OIDC provider | via `enable_irsa` | backs IRSA |
| IRSA role `opensteward-eso` | `aws_iam_role` | trusts the chart KSA; least-privilege `secretsmanager:GetSecretValue` on the two secrets above |

### Prerequisites this Terraform does NOT install

Two **in-cluster add-ons** are prerequisites for the overlay and are
intentionally left out of this apply (keeps the graph a clean, provider-only
graph with no dependency on the kube-apiserver endpoint). Install them with Helm
**after** the cluster is up and before `helm install`ing OpenSteward:

```sh
# 1. AWS Load Balancer Controller — renders the chart's `ingressClassName: alb`.
#    Needs its own IRSA role; follow the controller's install guide:
#    https://kubernetes-sigs.github.io/aws-load-balancer-controller/
helm repo add eks https://aws.github.io/eks-charts
helm install aws-load-balancer-controller eks/aws-load-balancer-controller \
  -n kube-system --set clusterName=$(terraform output -raw cluster_name)

# 2. External Secrets Operator — renders the chart's ClusterSecretStore and
#    syncs opensteward/app-secrets into the in-cluster Secret.
helm repo add external-secrets https://charts.external-secrets.io
helm install external-secrets external-secrets/external-secrets -n external-secrets --create-namespace
```

The `opensteward-eso` IRSA role created here is what ESO assumes (via the chart
ServiceAccount). The AWS LB Controller's IRSA role is separate; this
reference does not create it — follow the controller's install guide (linked above).

## Apply order

```sh
cp terraform.tfvars.example terraform.tfvars   # edit region, release/namespace, sizing
terraform init
terraform apply

# point kubectl at the new cluster
aws eks update-kubeconfig --region $(terraform output -raw region) \
  --name $(terraform output -raw cluster_name)

# install the two prereq add-ons (see above), then OpenSteward:
helm install os ../../helm/opensteward \
  -f ../../helm/overlays/aws-values.yaml -f my-secrets-and-hosts.yaml \
  --namespace opensteward --create-namespace
```

> The Helm release name (`os`) and `--namespace` (`opensteward`) **must** match
> `helm_release_name` / `k8s_namespace` in your tfvars — the IRSA trust policy is
> scoped to `system:serviceaccount:<namespace>:<release>-opensteward`. Mismatch
> ⇒ ESO can't assume the role ⇒ secrets never sync.

## Mapping outputs → overlay placeholders

After `terraform apply`, run `terraform output` and paste into the overlay:

| Overlay location | Placeholder | Terraform output |
|---|---|---|
| `secrets.externalSecrets.aws.region` | `<REGION>` | `region` |
| `serviceAccount.annotations."eks.amazonaws.com/role-arn"` | `arn:aws:iam::<ACCOUNT_ID>:role/opensteward-eso` | `eso_irsa_role_arn` (full ARN) |
| `ingress` ... `certificate-arn` | `<REGION>` / `<ACCOUNT_ID>` / `<CERT_ID>` | `region`, `account_id`, + ACM (see `acm_certificate_arn_guidance`) |
| `publicUrls` / `ingress.hosts` | `admin.example.com`, `api.example.com`, ... | your DNS (point records at the ALB) |
| `secrets.externalSecrets.remoteSecretName` | `opensteward/app-secrets` | `app_secrets_name` (already matches the default) |
| `redis.url` | `<ELASTICACHE_PRIMARY_ENDPOINT>` | not provisioned here — see Redis note below |

The `account_id`, `cluster_name`, `rds_endpoint`, and
`cluster_oidc_provider_arn` outputs are informational / for the add-on installs.

### The `opensteward-db` Kubernetes Secret (DATABASE_URL)

The overlay's `database.external.existingSecret: opensteward-db` is **not**
created by Helm. Create it once from the Terraform output:

```sh
kubectl create secret generic opensteward-db -n opensteward \
  --from-literal=DATABASE_URL="$(terraform output -raw database_url)"
```

`database_url` is a **sensitive** output (it embeds the DB password), so it never
prints in plan/apply logs — use `terraform output -raw database_url`.

Prefer GitOps? The same value lives in the `<prefix>/db-credentials` Secrets
Manager secret (output `db_credentials_secret_name`, key `DATABASE_URL`); add an
`ExternalSecret` so ESO syncs it into `opensteward-db` instead of `kubectl
create`.

### Redis (optional)

The overlay's `redis.url` expects an ElastiCache primary endpoint, but the base
chart only *requires* Redis once you scale `integration-server` past one replica.
ElastiCache is intentionally **not** in this reference (it's a small, independent
add). Either provision an ElastiCache (Redis OSS / Valkey, TLS) replication group
in the private subnets and paste its primary endpoint into `redis.url`, or set
`redis.enabled: false` and keep `minReplicas: 1` for a first bring-up.

## STORE_SECRET — read this before re-applying

`STORE_SECRET` encrypts application data **at rest**. It is generated **once** and
**must never change** — rotating it makes existing encrypted data unrecoverable.

Two safeties enforce this:

- `random_password.store_secret` has `lifecycle { ignore_changes = all }`.
- `aws_secretsmanager_secret_version.app` has `ignore_changes = [secret_string]`,
  so no future `terraform apply` rewrites the JSON blob (JWT/SESSION/STORE).

A `terraform destroy` **will** delete the Secrets Manager secret (recovery window
0 in this reference for clean rebuilds). If you care about the data, take a copy
of the `STORE_SECRET` value first, or set `recovery_window_in_days` > 0 and enable
`db_deletion_protection`/`prevent_destroy` for production.

## Production hardening checklist (left lean on purpose)

- `db_multi_az = true`, `db_deletion_protection = true`, longer backups.
- `single_nat_gateway = false` for per-AZ egress HA (edit `network.tf`).
- Lock `cluster_endpoint_public_access_cidrs` to your office/VPN, or set
  `cluster_endpoint_public_access = false` and use a bastion/VPN.
- Move state to a remote backend (S3 + DynamoDB lock) — none is configured here.
- Consider RDS-managed master password rotation (`manage_master_user_password`)
  + an `ExternalSecret` over the RDS-managed secret, instead of the static one.
