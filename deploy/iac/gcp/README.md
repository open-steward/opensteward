# OpenSteward — GCP / GKE reference Terraform

Reference (example) infrastructure-as-code that provisions exactly what the
OpenSteward Helm GCP overlay expects:
**`deploy/helm/overlays/gcp-values.yaml`**.

It is meant to be **read and adapted**, not run blind. It favours clarity and
correctness over completeness, pins provider versions, and never hardcodes real
secrets (app secrets and the DB password are generated by the `random` provider).

## What it provisions

| File | Resources |
|------|-----------|
| `apis.tf` | Enables the required Google APIs |
| `network.tf` | VPC, subnet (GKE secondary ranges), Cloud NAT, Private Services Access for Cloud SQL private IP |
| `gke.tf` | Regional GKE cluster with **Workload Identity** + a lean autoscaling node pool (`GKE_METADATA`) |
| `cloudsql.tf` | Cloud SQL for PostgreSQL (private IP preferred), app DB + user, generated password |
| `memorystore.tf` | Memorystore (Redis) — **optional** (`enable_memorystore`) |
| `secrets.tf` | `opensteward-app-secrets` Secret Manager secret (JSON), `opensteward-eso` Google SA, `secretAccessor` grant, Workload-Identity binding to the chart KSA |
| `outputs.tf` | Every value you paste into the overlay |

## In-cluster PREREQUISITES (not created here)

This Terraform stops at the cloud boundary. Before `helm install`, install these
into the cluster (Workload Identity is already enabled on the cluster by `gke.tf`):

- **ingress-nginx** — the overlay sets `ingress.className: nginx`
- **cert-manager** — plus a `ClusterIssuer` named `letsencrypt-prod` (the overlay's
  `tls.certManager.clusterIssuer`)
- **External Secrets Operator (ESO)** — renders the `ClusterSecretStore` /
  `ExternalSecret` the overlay turns on (`secrets.externalSecrets.createStore: true`)

```sh
helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx
helm repo add jetstack https://charts.jetstack.io
helm repo add external-secrets https://charts.external-secrets.io
helm install ingress-nginx ingress-nginx/ingress-nginx -n ingress-nginx --create-namespace
helm install cert-manager jetstack/cert-manager -n cert-manager --create-namespace --set crds.enabled=true
helm install external-secrets external-secrets/external-secrets -n external-secrets --create-namespace
# then create the letsencrypt-prod ClusterIssuer
```

## Apply order

1. **Authenticate & set the project**
   ```sh
   gcloud auth application-default login
   gcloud config set project <PROJECT_ID>
   ```
2. **Configure**
   ```sh
   cp terraform.tfvars.example terraform.tfvars   # edit project_id, release name, sizing
   ```
3. **Provision the cloud resources**
   ```sh
   terraform init
   terraform apply
   ```
   APIs → network → GKE → Cloud SQL → Secret Manager + IAM come up in dependency
   order. The Cloud SQL private IP waits on the VPC peering automatically.
4. **Get cluster credentials**
   ```sh
   gcloud container clusters get-credentials "$(terraform output -raw cluster_name)" \
     --region "$(terraform output -raw cluster_location)"
   ```
5. **Install the in-cluster prereqs** (ingress-nginx, cert-manager + issuer, ESO — above).
6. **Create the namespace and the DB secret**
   ```sh
   kubectl create namespace opensteward
   kubectl -n opensteward create secret generic opensteward-db \
     --from-literal=DATABASE_URL="$(terraform output -raw database_url)"
   ```
7. **Fill the overlay placeholders** (table below), then install the chart:
   ```sh
   helm install os deploy/helm/opensteward \
     -f deploy/helm/overlays/gcp-values.yaml \
     -f my-secrets-and-hosts.yaml
   ```
   The release name (`os`) MUST match `helm_release_name` — the chart's KSA is
   `<release>-opensteward`, which is what the Workload Identity binding targets.

## Output → overlay placeholder map

Run `terraform output` and paste each value into
`deploy/helm/overlays/gcp-values.yaml`:

| Terraform output | Overlay field | Placeholder |
|------------------|---------------|-------------|
| `project_id` | `secrets.externalSecrets.gcp.projectID` | `<PROJECT_ID>` |
| `cluster_location` | `secrets.externalSecrets.gcp.clusterLocation` | `<REGION_OR_ZONE>` |
| `cluster_name` | `secrets.externalSecrets.gcp.clusterName` | `<CLUSTER_NAME>` |
| `eso_gsa_email` | `serviceAccount.annotations[iam.gke.io/gcp-service-account]` | `opensteward-eso@<PROJECT_ID>.iam.gserviceaccount.com` |
| `app_secret_name` | `secrets.externalSecrets.remoteSecretName` | `opensteward-app-secrets` (already the overlay default) |
| `redis_url` | `redis.url` | `redis://<MEMORYSTORE_IP>:6379` |
| `database_url` | the `opensteward-db` K8s secret (`DATABASE_URL`) | referenced via `database.external.existingSecret` |

`project_id` also appears in the ESO annotation domain. The overlay's `ingress.hosts`
and `publicUrls` are yours to set in `my-secrets-and-hosts.yaml` — not derived here.

## Database: private IP vs. the Auth Proxy

- **Private IP (default, `use_private_ip = true`)** — the instance gets a private
  IP on the VPC; pods reach it directly. `database_url` is built against that IP.
- **Auth Proxy alternative (`use_private_ip = false`)** — the instance has no
  private IP; run the Cloud SQL Auth Proxy as a sidecar and point the app at
  `127.0.0.1:5432`. `database_url` is emitted in that 127.0.0.1 form, and
  `cloudsql_connection_name` is what you pass to the proxy:
  ```
  cloud-sql-proxy <cloudsql_connection_name> --private-ip
  ```
  The sidecar authenticates with the same Workload Identity SA (grant it
  `roles/cloudsql.client` if you go this route).

`database_url` and `database_password` are **sensitive** — read them explicitly
(`terraform output -raw database_url`); they won't print in the plain output table.
The password lives only in Terraform state and that secret; this stack does not
write it to Secret Manager.

## STORE_SECRET — do not rotate, do not casually destroy

`opensteward-app-secrets` is one JSON object: `JWT_SECRET`, `SESSION_SECRET`,
`STORE_SECRET` (and `ADMIN_SECRET` when `include_admin_secret = true`).

`STORE_SECRET` encrypts application data **at rest**. It is generated **once** and
must never change — rotating it makes existing encrypted data unreadable. This stack
guards it two ways:

- the `random_password.store_secret` has `lifecycle { ignore_changes = all }`
- the `google_secret_manager_secret_version` has `lifecycle { ignore_changes = [secret_data] }`

so a re-`apply` will **not** silently rotate it. Note the sharp edge:
**`terraform destroy` deletes the secret** — that is equivalent to destroying your
data-encryption key. To rotate the *rotatable* keys (JWT/SESSION/ADMIN)
deliberately, add a new Secret Manager version out-of-band rather than editing this
code.

## Memorystore (Redis)

Off by default. Set `enable_memorystore = true` to provision it, then paste
`redis_url` into the overlay's `redis.url`. The lean instance has AUTH and
in-transit encryption **off** (so `redis://`). For production enable
`auth_enabled` + `transit_encryption_mode` on the instance and switch the overlay
to `rediss://`. If you already run Redis elsewhere, skip this and set `redis.url`
by hand.

## Provider versions

Pinned in `versions.tf`: `google` and `google-beta` `~> 6.12`, `random` `~> 3.6`,
Terraform `>= 1.5`. Bump deliberately and re-`plan`.
